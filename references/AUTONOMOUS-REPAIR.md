# Автономное исследование и исправление

Применяй при новой сложной функции, найденном дефекте, наследовании незнакомого проекта или просьбе усилить качество. Для ясной низкорисковой правки достаточно её проверки; не навязывай весь процесс.

## Сначала установи факты

Восстанови цель, разрешённые действия и инварианты из задания и текущего проекта. Прочитай инструкции репозитория, точки входа, зависимости/lockfile, существующие тесты и последние изменения. Отдели дефект продукта от дефекта теста, данных, окружения и внешнего сервиса. Не изменяй рабочие данные пользователя ради воспроизведения.

Сними исходное состояние: точная версия, команда/сценарий, фактический результат, ожидаемый результат и основание ожидания. Существующий зелёный тест — только исходная точка: он может не проверять жалобу. Принимаемые решения опираются на пользовательское требование, спецификацию, протокол или независимый расчёт, а не на текущую реализацию.

## Исследуй ровно то, что меняет решение

Иди по цепочке: локальный код и воспроизведение → официальная документация нужной версии → исходники и тесты зависимости → issue с воспроизведением. Для проектных решений сравни несколько подходов по совместимости, проверяемости, сопровождению и цене. Записывай источник, дату, версию и вывод; README и популярность не доказывают работоспособность. Недоступный источник не считается прочитанным.

Для неоднозначного бага сформулируй несколько конкурирующих причин. Для каждой укажи наблюдение, которое её опровергнет. Исследуй прохождение данных между границами: ввод → состояние → хранение/API → представление → восстановление. Собери минимальные диагностические данные без токенов и личного содержимого. Сравни с соседним работающим сценарием. Выбирай следующий эксперимент по способности различить причины, а не по лёгкости очередного патча.

Заверши исследование, когда причины достаточно для ограниченного исправления и известна проверка; продолжай, если остаётся существенное противоречие. Не читай бесконечно и не подменяй исследование списком ссылок. Независимый просмотр кода полезен при спорной причине, гонке, миграции, правах или внешнем эффекте; используй реального исполнителя только если это разрешено средой.

## Цикл исправления

1. Воспроизведи дефект на изолированных данных. Для ошибки логики/данных создай минимальную регрессионную проверку и убедись, что она падает по нужной причине до патча. Для визуальной мелочи достаточно точных шагов и снимка до/после. Если воспроизвести нельзя, не выдумывай RED: обозначь это и собери доступные данные.
2. Проверь гипотезу одним ограниченным изменением или наблюдением. Не накладывай несколько неподтверждённых исправлений. Отклонённую гипотезу запиши коротко, чтобы не повторять её после смены контекста.
3. Исправь источник ошибки в пределах задания. Сохрани пользовательские данные, публичные контракты, утверждённый дизайн и несвязанные изменения. Временно отключённую функцию не выдавай за исправленную.
4. Запусти исходный сценарий, соседние ветки и подходящие существующие тесты. Для важной логики докажи чувствительность теста: он падает на исходном дефекте или на контролируемой мутации в временной копии. Не удаляй проверки и не ослабляй ожидания ради зелёного результата.
5. Проверь конечный пользовательский путь в реальном доступном runtime. Внутренний вызов не заменяет клик, локальная версия не заменяет опубликованную, формула не заменяет пересчитанную таблицу. Сохрани фактические доказательства и точную границу проверки.

После двух неудачных исправлений одной причины прекрати повторять её: пересмотри модель, расширь воспроизведение или привлеки разрешённый независимый взгляд. Это не автоматический вопрос пользователю и не конец задачи. Продолжай, пока есть новый проверяемый путь в рамках полномочий. Эскалируй только точный недостающий доступ, обязательный выбор или непреодолимый блокер; перечисли уже проверенное и ближайшее действие. Никаких бесконечных перезапусков одного теста до случайного PASS.

## Что исправлять самостоятельно

Сразу исправляй подтверждённые баги в затронутом сценарии, очевидную регрессию, несовместимые подписи, доступность основного действия, потерю состояния, неверную обработку ошибок и соседние проявления той же причины. Обновляй зависимые переводы, инструкции и тесты. Обычные технические решения принимай сам.

Новая функция, смена цели, визуального направления, бизнес-правил, платформы или массовая перестройка не следуют из «сделай качественно». Если такую перемену уже явно делегировали, выполняй; иначе подготовь конкретный выбор. Учитывай уже данные разрешения, не проси их повторно. Платежи, публикация, пересылка данных и разрушительные действия остаются в полномочиях пользователя и правилах среды. Тестирование не даёт права атаковать чужие сервисы или отправлять настоящие заявки.

## Состояние и восстановление

Для приложения со хранением сначала опиши владельца состояния, стабильные ID, схему, моменты записи и восстановления. Проверяй отмену, повторное сохранение, старую схему, повреждённые записи, недоступное хранилище, несколько вкладок и поздние async-ответы. Смена языка или вида не меняет данные, если это не явное правило продукта.

Сброс/удаление — граница жизненного цикла: отменить или обесценить старые задания, остановить очереди и автосохранение, очистить только принадлежащие продукту данные, проверить очистку, затем открыть новое состояние. Учитывай резервные копии и восстановление после навигации. Уже выполненный внешний эффект нельзя «отменить» отменой Promise. Повторная доставка не должна дублировать эффект: нужен ключ операции или другая проверяемая идемпотентность, если это требуется контрактом.

## Учись без самовольного переписывания правил

В проекте сохраняй только подтверждённый урок: симптом → причина → минимальный пример → регрессионная проверка → границы применимости. Удали экспериментальные обходы, когда они перестали быть нужны. Общий навык или личную память меняй лишь при соответствующем разрешении; не размножай проектный частный случай на всех пользователей. При разрешённом обновлении навыка сохрани прежнюю версию, добавь поведенческий тест, сравни результат и синхронизируй устанавливаемую и выдаваемую копии.

Долгая работа должна восстанавливаться из короткой записи: цель, текущий артефакт, версия, открытые гипотезы, последний результат, следующий эксперимент. Не сохраняй секреты. После передачи работай дальше только при реальном механизме запуска и согласованном объёме; файл навыка сам не следит за будущими проектами.
