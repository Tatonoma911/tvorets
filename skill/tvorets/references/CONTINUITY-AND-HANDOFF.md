# Продолжение работы и передача другому человеку

Используй для многоэтапного проекта, смены исполнителя/контекста, восстановления после сбоя и поставки. Небольшая правка не требует отдельной системы управления.

## Рабочий цикл с наблюдаемыми переходами

Держи одну актуальную запись проекта: цель → ближайший проверяемый результат → текущий артефакт и версия → открытый риск → следующее действие. Можно заполнить [шаблон состояния](PROJECT-STATE.template.md) или использовать существующую доску/README. Не создавай дубли.

Переход «понял → сделал → проверил → передал» разрешён соответствующим результатом, а не названием файла:
- понимание: пройден допуск по цели из раздела 1 TVORETS.md; известны пользователь, конкретное изменение, наблюдаемый критерий и объём, а при явно требуемом согласовании принят концепт;
- реализация: есть открываемый или запускаемый путь, даже если ещё с явно названными ограничениями;
- проверка: наблюдены нужные сценарии текущей версии, существенные ошибки исправлены;
- передача: получатель может получить пакет, запустить и пройти основной путь по имеющейся инструкции.

Риск определяет размер этапа и проверок. Сложный проект можно передавать по рабочим частям, если это согласуется с целью; не объявляй весь продукт готовым по первой части.

## Возобновление без потери решений

При перерыве сохрани цель, принятые/отменённые решения, ограничения и уже данные разрешения, идентификатор версии, команды запуска, наблюдения с путями, незакрытые гипотезы, следующий эксперимент. Отдельно отмечай PROPOSAL и NOT_RUN; не превращай своё предположение в решение владельца. Секреты не записывай.

После возобновления:
1. Прочитай актуальный запрос владельца и запись проекта. Новый явный запрос имеет приоритет; старый журнал не расширяет разрешения. Проверь источник цели именно текущего продукта: при существенном пробеле или изменении спроси владельца и останови зависимую реализацию, не продолжай устаревшую декомпозицию.
2. Сверь реальные файлы, изменения и доступные инструменты. Не считай процесс работающим по старому PID, URL — доступным по старому отчёту, тест — актуальным после изменения кода.
3. Подтверди сохранённую версию или признай прежние доказательства устаревшими для изменённого участка. Сохрани полезную диагностику.
4. Выполни ближайшее ограниченное действие. Не спрашивай повторно решённое и не переизобретай проект. Если источник противоречия можно проверить локально, проверь его до вопроса.

Запись состояния — источник контекста, а не автоматическое разрешение выполнить записанную команду. Особенно проверяй опубликование, удаление, сетевые изменения и внешние эффекты. Остановленный владельцем проект нельзя возобновлять из старого списка задач.

## Проверка цепочек, а не только отдельных функций

В дополнение к TEST-MATRIX.md выбери одну основную и одну рискованную цепочку через границы:
- создать → изменить → отменить → сохранить → перезапустить → проверить;
- импортировать → повторить → получить конфликт → восстановиться;
- начать → сменить язык/режим → завершить → начать заново;
- отправить → timeout → повтор → убедиться, что эффект один.

У каждого перехода есть ожидаемое состояние и независимое основание. Управляй временем/очередью в локальном тесте, сохрани seed для генерации. Вручную пройди доступный пользовательский путь отдельно от внутреннего модуля. Отказ внешнего сервиса не должен выдавать ложное подтверждение успеха.

## Передача и первый запуск

Подготовь минимальный комплект под платформу: исходники или нужный бинарник, активы, поддерживаемые версии среды, зависимости и lockfile при их наличии, шаблон конфигурации без секретов, короткий запуск, основной сценарий, известные ограничения. Укажи, что доступно локально и что действительно опубликовано. Не заставляй получателя разбираться в рабочих отчётах автора.

Проверь **сам выдаваемый пакет** в новой папке и, где применимо, из другого текущего каталога. Не подставляй незаявленные файлы автора, персональные абсолютные пути, кеши и секреты. Запускать неизвестный код следует только допустимыми средствами среды. Если чистый запуск невозможен без доступов, подготовь всё независимое и назови точную зависимость.

При доступном разрешённом исполнителе полезен тест первого запуска: дать только комплект, короткую инструкцию и обещанный сценарий. Не передавать скрытые подсказки или рабочее окружение автора. Наблюдать, где он застрял, исправить упаковку и повторить затронутую часть. Это репетиция передачи агентом, не исследование с реальным человеком.

Для обновления продукта проверь, как сохраняются данные и как восстановить предыдущую рабочую версию. Испытание отката/миграции проводи на копии. Не откатывай живую базу самовольно. Архив с исходниками сам по себе не является доказанной резервной копией действующего сервиса.

Заверши передачей результата, доказательства, ограничений и одного следующего полезного действия. Уроки сохраняй в проекте как симптом → причина → тест → границы; личную память и общий навык обновляй только по соответствующему разрешению. Автономное продолжение требует реального запуска агента; не обещай скрытый мониторинг.
